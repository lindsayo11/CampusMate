# CampusMate Stage33：Zulip Campus 前端重构

版本：v0.33.0-workspace.1。参考用户提供的 `CampusMate_01-06_Combined_UI.html` 中 04 Zulip Campus。此次修改实际 Next.js 前端，继续使用现有后端、鉴权和持久数据库。

## 设计与信息架构

采用深灰蓝顶栏、浅灰导航、发展频道色标、主题分组内容区和相关信息侧栏。全站统一字体、间距、表单、按钮、加载状态、空状态、错误反馈与移动导航。图标为本地 SVG；中文界面字体为本地 Noto Sans SC 子集，附 SIL OFL 授权，未覆盖字符回退系统字体，运行不依赖第三方字体服务。

- 学生工作台：当前事项、个人待办、会话未读、后续日程、发展频道和助手入口。
- 信息中心：按发展路径、关键词、地区和有效状态筛选；分页；查看版本、原文、规则与证据；关注、加入计划、进入资格助手。
- 校园机会：实习、竞赛、考公、志愿、社团、升学的独立列表，保留原详情、资格、行动和提醒功能。
- 发展路径指南：新增 `/paths`，展示路径说明与参考准备节点，并进入相关信息或生成计划。
- 个人计划：系统生成的来源编号已转换为可点击的事项与原文入口。`/tracker` 同时承接 UserPlan 个人计划与原机会 Tracker 行动；新增手动创建、编辑、路径筛选、看板/列表切换、状态更新和提醒入口。`/actions` 统一重定向至此。
- 发展助手：会话列表、用户/助手对话、功能和路径选择、结果卡片、资格选择、写入预览、确认/取消与历史恢复。计划从下拉框选择，不要求用户输入内部编号。
- 交流空间：会话侧栏、未读数、消息流、房间内输入、技能匹配、举报、拉黑，保留持久化和断线补齐。
- 团队管理：统一创建、邀请、成员、任务和房间入口的排版。
- 通知中心：按个人计划、关注事项、团队任务、校园机会分组，可定位各类别。
- 个人资料：补齐发展目标、年份、地区、学历、语言成绩及科研/实习/竞赛/创业经历。保存基本资料时一并保留这些字段，避免后端默认值覆盖已有信息。
- 运营后台：独立导航、概览、数据接入、来源管理、审核、举报、审计与运行状态。原管理页面继续使用既有 API，统一视觉和组件样式。

## 学生与管理员的权限

| 能力 | 普通用户 | 管理员 |
| --- | --- | --- |
| 浏览公开信息、原文与机会 | 可使用 | 可使用 |
| 个人画像、计划、提醒、Agent 会话 | 仅当前账号 | 仍仅当前账号，不自动查看他人私有记录 |
| 房间消息和团队任务 | 仅已加入的房间；遵守队长/负责人权限 | 管理员身份不自动加入其他团队 |
| 创建团队、邀请、分配任务 | 自己创建的团队由队长管理 | 同样遵循团队角色 |
| 数据源、平台导入、审核和发布 | 不开放 | 专属运营后台 |
| 平台文档删除、撤回 | 不开放 | 管理员执行并保留审计 |
| 举报处理和操作审计 | 只能查看自己的举报 | 处理举报、查看运营审计 |

管理员从学生工作台的专属入口进入 `/admin`，可随时切回学生视图。视图切换不会更换账号，不会扮演其他学生。侧栏头像区和个人资料页显示实际角色。

角色来自后端 `/v1/account`。生产环境由有效登录身份以及服务端 `ADMIN_USER_IDS` 用户 ID 白名单决定，用户不能在注册表单中把自己设为管理员。界面隐藏和页面访问限制之外，管理接口继续由后端 `require_admin` 校验。前端代理不转发浏览器提供的演示身份请求头。

本机演示脚本默认将 `demo-user` 配置为管理员，因此能查看两套工作界面。正式部署需要关闭 `DEMO_MODE` 并配置登录服务；不要把这个演示身份机制作为线上角色控制。

## 数据发布规则

沿用 Stage31：系统导入通过完整性校验后直接展示；手动导入经审核后展示；平台内容删除由管理员执行。前端文件导入属于手动导入，在草稿与审核流程内处理。本次更新了旧的“所有内容均需双人发布”说明，避免与系统导入规则冲突。

页面展示的数据与数量来自业务接口，无随机在线人数、虚构成员或伪造运营指标。原演示事项仍显示模拟标记与测试批次。参考图中的多级 Topic 独立消息模型、私信导师、附件/表情等没有现成后端支持的功能，没有做成假按钮；当前按真实房间组织聊天，按发展频道/事项组织信息。

## 启动与验收

沿用现有环境变量与迁移方式。首次启动脚本已修正依赖顺序：先由 dev.sh 创建环境并安装依赖，再执行迁移，避免新解压源码缺少 .venv 时失败。无需新数据库迁移，当前 schema 仍为 0023。

```bash
bash scripts/start_retained_demo.sh
```

打开 `http://127.0.0.1:3000/`。助手需要 `ENABLE_AGENT_UI=true`；保留的演示启动脚本已开启。生产环境按既有部署文档配置身份、数据库与 Worker。

浏览器验收工具：`scripts/ui_acceptance.py`，先执行 `npm run build --prefix frontend`，配置 `CHROMIUM_PATH` 后运行。它以现有演示库的独立副本启动管理员/学生两个后端与前端实例，运行桌面及移动端 Playwright 验收，并在退出时关闭服务。

```bash
CHROMIUM_PATH=/你的/Chromium路径 backend/.venv/bin/python scripts/ui_acceptance.py
```

验收包括：信息筛选、计划保存与刷新、资料字段保留、助手确认写入、资格查询、双账号团队邀请/任务/聊天/举报、角色入口与服务端拒绝、主要页面无水平溢出。截图位于 `artifacts/stage33/`。

验证结果：19 项前端单元测试通过；TypeScript 检查与最终生产构建通过。完整运行 40 项桌面/移动浏览器用例，39 项首次通过；画像表单在已有内容下的精确标签定位问题修复后，桌面和移动 2 项针对性复验均通过。因此这 40 项场景已全部验证通过。主页面测试覆盖 28 个地址的两种视口；包含学生隐藏管理入口、直达后台拦截，以及伪造 X-User-Id 访问管理代理仍为 403。截图阶段未发现浏览器脚本异常。本轮没有重新声称完成真实 Supabase、Dify、PostgreSQL 或历史迁移验收。

## 模型接口与语义检索的通俗说明

真实模型接口已经保留并实现调用：平台将用户需求交给 Dify 工作流识别工具和参数，再由服务端查询画像、路径、事项、规则和计划；查询结果可交给模型生成自然语言解释。写入仍需用户确认，模型没有任意修改数据库或管理员操作权限。接入真实服务还需要工作流与密钥，不能只填一个任意模型地址。

语义向量库的作用是按意思找资料。例如用户说“毕业后想进体制内”，语义检索有机会找到“公务员招录”“事业单位招聘”等不同措辞的材料，再把相关原文交给模型解释。它不代替正式业务数据库，也不自动保证资格判断正确。当前本地稀疏检索主要依赖文字片段重合；尚未实现上述生产语义检索。
